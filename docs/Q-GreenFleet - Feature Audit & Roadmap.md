# Q-GreenFleet - Feature Audit and Roadmap

**Audit date:** 2026-10-04
**Repository audited:** Q-Flow / SIH26138  
**Scope:** Source code, frontend routes/components, backend tests, committed metrics, and project documentation.

**Latest data validation:** MRV registry rebuild completed on 2026-10-03 from 25,741 vessels; GFW registry contains 5,850 records and 4,526 gross-tonnage matches. A one-minute AIS refresh completed with zero broadcasts, so AIS remains available as an integration but has no new observations in the local refresh.

**Generated development datasets:** `Datasets/Synthetic/fuel_prices_monthly.csv` (360 rows), `port_delays.csv` (5,000 rows), `vessel_telemetry.csv` (10,000 rows), and `port_network.csv` (12 routes), generated by [generate_synthetic_extensions.py](../backend/data/generate_synthetic_extensions.py) with seed `20261003`. Their limitations are recorded in `Datasets/Synthetic/MANIFEST.json`; they are synthetic proxies, not measured or regulatory data.

## Executive summary

The previous version of this document treated every capability as proposed because it did not have repository evidence. That is no longer accurate. The repository contains a functional prototype with a working ship and road optimization path, lifecycle emissions and cost calculations, constraint repair and independent validation, provenance APIs, scenario save/load, frontend dashboards, and reproducible benchmark artifacts.

The implementation is not yet a production fleet-management product. Vessel and extension datasets are prototype data, scenario storage is file-backed, and some fuel factors/prices are representative assumptions. Advanced features now have prototype slices for calibrated uncertainty, telemetry twin reporting, and synthetic green-corridor selection, but they are not production or regulatory systems.

## What is available today

The following end-to-end path is present in code:

1. Select ship or road mode and configure distance, cargo, deadline, vessels/vehicles, fuels, weather, and operating assumptions.
2. Validate scenario inputs.
3. Predict fuel/energy using the prediction or physics path.
4. Calculate fuel cost, shore-power cost, lifecycle WtT/TtW/WtW emissions, and optional caps.
5. Run MO-QPSO with constraint repair and return a Pareto set plus a balanced recommendation.
6. Re-check constraints independently on returned plans.
7. Compare QPSO with NSGA-II/classical baselines and inspect provenance/experiment metadata.

### Optimization UI update (2026-10-04)

The frontend optimization view now exposes the three objectives in one consistent
visual and keeps the balanced recommendation values tied to the preference sliders:

- The Pareto chart is fixed to operating cost (INR) versus WtW GHG (tCO2e), with
  readable axis spacing and cost tick formatting.
- A connected line orders the returned plans by cost to show the trade-off frontier;
  fuel-colored markers remain selectable and the legend includes every returned fuel.
- The previous chart axis-pair toggle is no longer used on this view.
- Each Fuel, Cost, and GHG preference slider shows both the Original baseline value
  and the current Optimized TOPSIS value. Moving a slider updates the optimized
  values live from the weighted recommendation.
- Cost values displayed by the optimization path are clamped at zero, so a savings
  recommendation cannot produce a negative cost.

### Phase 1 stabilization progress

The first stabilization slice is now implemented:

- `GET /api/status` exposes the active predictor version, calibration basis, synthetic-fleet status, fuel-factor status, and scenario-storage status.
- Scenario records now persist to `results/scenarios/scenarios.json`, expose schema version/revision/timestamps, and support list/load endpoints.
- Fleet records now persist to SQLite at `results/fleet/fleet.db`; `/api/vessels` supports create, update, delete, availability history, and the optimizer uses the persisted pool. `/api/fleet/storage` reports schema/readiness state and `/api/fleet/backups` creates admin-only consistent backups.
- `/api/fuels/pathways` provides versioned pathway factors, source provenance, and representative availability labels.
- `/api/scenarios/compare` compares persisted scenario records by ID and reports missing records.
- `/api/predict/fuel` returns current-input counterfactual drivers for the local explanation chart.
- `/api/compliance/cii` and the Emissions screen provide an explicitly indicative CII-style KPI check.
- `/api/data/status` and the Provenance screen report local MRV, ERA5, AIS, GFW, registry-artifact, and live-credential availability.
- `/api/optimize/robustness` and the Scenario screen run a repeatable normal/adverse/severe weather stress test with fixed seeds and budget.
- The robustness endpoint now adds Monte Carlo weather, prediction-error, fuel-price, and delay draws with confidence intervals and feasibility probabilities; assumptions are returned with every result.
- Synthetic calibration statistics are now calculated from the generated fuel-price, port-delay, and telemetry files and returned in the robustness assumptions.
- `GET /api/digital-twins/{vessel_id}` provides a prototype telemetry summary and drift signal; `POST /api/corridors/optimize` ranks synthetic green-corridor alternatives.
- Live optimization responses include `engineMetadata`, and the Optimization screen displays the calculation context.
- The Optimization screen renders the cost-vs-WtW Pareto line and live Original/Optimized objective values for balanced slider selection.
- The Prediction screen reloads distinct deterministic prototype samples for its Time holdout and Vessel holdout controls, and shows an explicit empty state when live validation data is unavailable.
- Optimization requests default to `preserve_profit=true`; the baseline operating cost is exposed as the maximum cost ceiling and returned plans carry `profit_preserved` in their constraint report.
- Scenario, Prediction, and Provenance screens display whether they are using representative mock data or live backend mode.
- The frontend status banner reports the live model version and fleet-data status when `/api/status` responds; request-level fallback behavior remains visible as a limitation.
- `/api/models` reports model artifact presence, SHA-256, dataset metadata, and holdout metrics for prediction governance; optimizer recommendations carry the same provenance hashes in `engineMetadata`.
- `/api/health` includes fleet-storage readiness metadata; SQLite uses a busy timeout and autocommit initialization to tolerate concurrent health/backup access.
- Operational middleware now adds request IDs, redacted structured logs, security headers, and configurable per-client rate limiting; `/api/security/status` reports non-secret posture flags.
- `/api/benchmarks/confidence` reports 95% intervals when benchmark seed dispersion is available.
- Backend regression coverage now includes the status endpoint and optimization metadata contract.

Remaining work after this phase is frontend-to-backend identity/session integration, organization-level authorization, database migrations/backups, stronger live/fallback error presentation, and controlled model promotion/rollback.

The remaining partial statuses are now dependency-limited rather than unimplemented: calibrated optimizer ML needs a compatible labeled training target, uncertainty calibration needs historical delay/price observations, maritime live quality needs sustained source coverage, and regulatory KPI completion needs the applicable official reference lines and reporting rules.

Relevant entry points include [backend/app.py](../backend/app.py), [fleet_engine.py](../backend/optimization/fleet_engine.py), [lifecycle.py](../backend/emissions/lifecycle.py), [constraints.py](../backend/optimization/constraints.py), [Benchmarking.jsx](../frontend/src/pages/Benchmarking.jsx), and [Provenance.jsx](../frontend/src/pages/Provenance.jsx).

## EACF status

**EACF is now explicitly mapped for the prototype as Explainability, Accounting, Constraints, and Feasibility.** `POST /api/eacf/evaluate` combines those four evidence blocks and returns a `prototype_contract` status.

The mapped capabilities are:

- **Explainability:** SHAP feature-importance code and Prediction UI.
- **Accounting:** lifecycle emissions and cost engine.
- **Constraints/feasibility:** independent constraint report and repair tests.

If EACF was intended to mean something else, replace this mapping and its acceptance tests before using it as a product claim.

## Recommended roadmap

### P0 - Stabilize the implemented prototype

- Make the trained prediction model and its version explicit in optimizer runs.
- Keep scenario/run storage on durable infrastructure and add retention/backup policy.
- Connect frontend identity to backend roles, restrict CORS, add audit logs, and manage deployment secrets.
- Link outputs to exact dataset/model hashes and show synthetic versus measured data prominently.
- Add frontend/API tests for live mode, fallback behavior, exports, and error states.

The prototype telemetry model can be regenerated locally with `python prediction/train_synthetic_engine.py`; its ignored model artifact is intentionally not treated as a production-trained model.

### P1 - Complete the partial capabilities

- Connect frontend identity/token integration to fleet roles and add organization-level authorization.
- Add richer scenario result-delta charts and connect fuel sensitivity to regional data.
- Maintain local SHAP compatibility as tree-model versions change.
- Add official regulatory reference versioning and review.
- Operationalize MRV/ERA5/AIS/GFW ingestion with refresh and failure monitoring.

### P2 - Add research differentiation

- Continue calibrating uncertainty distributions as better operational data becomes available.
- Expand fuel-pathway intelligence with regional availability and provenance.
- Strengthen benchmark statistics and reproducibility reporting.
- Replace synthetic calibration/network data with approved historical and operational data.
- Add CI regression thresholds to benchmark claims.

### P3 - Advanced operational intelligence

- Adaptive vessel digital twins with live telemetry.
- Green-corridor and port-network co-optimization with licensed network data.
- Telemetry-driven recalibration, drift detection, and approval-controlled retraining.
